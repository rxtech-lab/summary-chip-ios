# Editorial headlines

`GET /api/v1/summaries/headlines` uses the existing bearer authentication and returns only the caller's own chips. Responses use `Cache-Control: no-store`.

The latest 50 chips whose kind is `summary` or `podcast` are evaluated together using `AI_EVALUATION_MODEL` (the existing decision model). Each receives an integer score from 0–100. The server sorts by `score × 0.5^(ageHours/24)`, then creation time and ID descending. The first is also returned as the legacy single-item `highlighted` field; it changes when the ranking or candidate set changes. Every chip scoring at least 70 is an Editor’s Pick, with no per-day limit. Each score and pick decision is stored in `editorial_scores`; re-evaluated chips can gain or lose the badge. Chips outside the latest-50 evaluation window retain their stored decision. All other kinds are excluded. Private chips remain private and can be shown only by the authenticated account's app/widget.

Response: `{ generatedAt: string | null, pending: boolean, items: Headline[], highlighted: Headline | null, editorPickIDs: string[] }`.
A Headline is `{ id: string, title: string, kind: "summary" | "podcast", shareUrl: string, createdAt: string, score: integer }`.
No chips returns `items: []`, `highlighted: null`, `pending: false`. Missing or obsolete ranking returns no items and `pending: true`, and schedules a refresh. `editorPickIDs` still returns persisted picks across all days while a refresh is pending, including picks outside the latest-50 window; deleted chips and other owners’ chips are excluded. Clients poll at bounded intervals. Disabled or failed decision evaluation never fabricates a production score. Existing auth errors apply.

Every summary/podcast insertion, including imports, Siri and daily podcast generation, schedules a fresh ranking after the response. A candidate revision and monotonic write fence prevent older evaluation results replacing newer results. Deletions and edits invalidate the revision; the next read schedules recomputation. Apply migrations 0038 and 0041 before deploying. Migration 0041 backfills per-chip decisions from existing ranking scores and cascades deletion with chips/accounts.

The app highlights every persisted pick with a yellow Editor’s Pick badge and an orange card border. The headline widget fetches the same authenticated result every 15 minutes (subject to WidgetKit scheduling), links to its chip, and hides cached content when the shared session ends. Siri's existing Add Summary shortcut uses the same insertion path.

The Editor’s Picks widget supports small (one pick), medium (two picks), and large (four picks) sizes. It groups picks from the most recent day containing a pick in the current ranking window, using the device calendar, and preserves ranking order within that day. Medium and large widgets label that day explicitly. It does not mix days or fill spare slots with chips that are not picks. With older servers, scores of at least 70 identify picks. Persisted picks outside the current ranking window are not included. Each tile opens its own chip. Cover artwork is fetched through the existing summary detail response and downloaded before the timeline is published, downsampled to 480 pixels; missing artwork uses a summary/podcast icon. Account identity is checked again after image loading.

The Feed filter menu and Filter sheet offer **Editor’s Pick**, combined with the other library filters. `GET /api/v1/summaries?editorsPick=true` returns only the caller’s persisted picks for summary/podcast chips, including older picks outside the current ranking window. The predicate runs before cursor pagination. Omit the parameter or use `false` for the normal library; other values are rejected. Offline filtering uses the pick IDs most recently loaded in the current session; without known decisions it shows no picks.

Chat agents can use `listEditorsPicks`; MCP clients can use the read-only `list_editors_picks` tool (`chippy:read`). Inputs: `date` (`YYYY-MM-DD`, `today` or `yesterday`, default `today`), optional IANA `timeZone`, `limit` (1–50, default 20), and `cursor`. The default zone comes from the caller’s most recently active registered device, falling back to UTC. Dates match chip creation time using local midnight boundaries, including daylight saving changes, rather than ranking time. Results include the resolved `date`, `timeZone`, `dateBasis: "createdAt"`, current saved scores, library cards in `results`, and `nextCursor`. Continue with the returned absolute date/time zone to page consistently. Picks are the current saved decisions, not historical ranking snapshots; private chips stay account-scoped.
